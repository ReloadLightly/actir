# ACTIR Statecraft Atlas Development Protocol

## Operating rule

ACTIR advances through small, falsifiable checkpoints:

> one question → one bounded change → one test → one result → review

No later stage begins merely because an earlier stage runs. Each pull request
states its single added capability, invariant, test evidence, and revision or
abandonment condition. A failed result is frozen before a repair is designed.

## Stage A — Build a trustworthy Atlas record

- **A.0 North-star contract:** replace the legacy prototype with the Statecraft
  Atlas purpose, axioms, epistemic boundaries, and search interface.
  No code or result.
- **A.1 Typed schema:** implement only versioned types for sources, evidence
  spans, discourse acts, action–mechanism claims, verification decisions,
  sequence links, policy programs, and decision dossiers.
- **A.2 Validation:** reject missing provenance, invalid epistemic states,
  inconsistent temporal order, and unauthorized transformations.
- **A.3 Fixture corpus:** create a tiny permission-safe, hand-authored corpus
  that contains clear cases, ambiguity, contradiction, inaction, and abstention.
- **A.4 Deterministic extraction contract:** transform fixture passages into
  candidate records without an API and compare them with a hand-coded gold set.
- **A.5 Verification and adjudication:** preserve extractor–verifier
  disagreement, revision history, abstention, and human resolution.

## Stage B — Retrieve statecraft rather than text

- retrieve actions and mechanisms for a dated decision query;
- distinguish discourse, reported action, explanation, and verified outcome;
- connect records into response and adaptation sequences;
- return analogous successes, failures, restraint, and inaction;
- test exact provenance, coverage, contradiction, and retrieval failure.

The first real corpus pilot begins only after the schema survives the fixture
corpus. It uses a maximum-diversity manifest, not an indiscriminate archive
download.

## Stage C — Produce a decision dossier

Compose retrieved records into a small set of conditional, inspectable policy
programs for a Japanese post-2022 decision question. Preserve objectives,
constraints, assumptions, resource commitments, reversibility, failure
conditions, provenance, and unresolved disagreement. Compare against direct
retrieval, fixed templates, and deliberate abstention.

## Stage D — Search for novel viable programs

Introduce an API-free `CandidateGenerator`, then behavioral descriptors and a
quality-diversity portfolio. Test whether search produces meaningfully distinct
high-quality programs rather than source-level variation or evaluator gaming.
Novelty is an intervention, not an assumed benefit.

## Stage E — Connect ShinkaEvolve

Implement ShinkaEvolve against the already frozen candidate and policy-program
interfaces. Run a zero-credential integration test first. Any paid comparison
uses identical evidence, evaluator, initial population, models, seeds, proposal
counts, dollar ceiling, and stopping rules for objective-only and
behavioral-novelty conditions.

## Evidence discipline

Every result is labeled as one of:

- contract test;
- development calibration;
- held-out validation;
- confirmatory result;
- future direction.

Once inspected, data remain development data. Fresh held-out evidence is
created only after the relevant schema, pipeline, evaluator, and thresholds
freeze.

Negative results remain first-class artifacts. A failed mechanism is not
silently repaired and reported as the original experiment; the failure and the
subsequent design change receive separate checkpoints.

## API discipline

Stages A.0–A.5 are API-free. API-assisted extraction begins only when:

1. the schema and gold fixtures are frozen;
2. deterministic parsing and validation already work;
3. the extractor and independent verifier have separate roles;
4. exact evidence spans are mandatory;
5. accuracy, agreement, calibration, abstention, and failure thresholds are
   predeclared;
6. an explicit dollar ceiling and resumable artifact path exist;
7. a human explicitly authorizes the run.

API use accelerates bounded extraction or search; it never substitutes for the
Atlas contract, epistemic validation, or human authority.
